## المرحلة A — مراجعة شاملة وحل المشاكل

### A1. مراجعة موديول بموديول
كل موديول بيتراجع بنفس قائمة الفحص:
1. **صحة المنطق:** الحسابات، الحالات الحدّية، التكرار، السباقات (race conditions).
2. **الأمان:** الصلاحيات على كل endpoint، عزل بيانات كل مركز (tenant)، الـ validation.
3. **الأخطاء:** رسائل واضحة بالعربي، مفيش فشل صامت في الواجهة.
4. **الأداء:** N+1 queries، pagination، indexes.
5. **الواجهة:** حالات التحميل والفراغ والخطأ، الموبايل.

الترتيب حسب خطورة الموديول على شغل العميل:

| # | الموديول | السبب |
|---|---|---|
| 1 | Finance (المالية والتحصيل والخزن) | فلوس — أي غلط فيها خسارة ثقة مباشرة |
| 2 | Sessions & Attendance (الحصص والحضور والدرجات) | أكتر شاشة بتتستخدم يوميًا |
| 3 | Students & Groups | أساس كل البيانات |
| 4 | WhatsApp & Telegram | خطر حظر الرقم + رسايل أولياء الأمور |
| 5 | Reports | أرقام بتتبعت لأولياء الأمور والإدارة |

| 8 | Settings / Backup / Upload | بيانات العميل |
| 9 | Subjects / Teachers / Dashboard / Barcodes / Spinner | الباقي |

## المرحلة B — الأداء

**الواجهة**
- الملف الرئيسي للـ JavaScript حجمه ~887KB (والطبيعي أقل من 300KB): تحليل بـ bundle visualizer، وفصل المكتبات الكبيرة.
- صفحة الباركود ~439KB: تحميل مكتبات الـ PDF والكاميرا عند الحاجة بس.
- الجداول الكبيرة (طلاب، مدفوعات، رسائل): pagination من السيرفر أو virtualization.
- ضبط cache الـ React Query عشان نقلل الطلبات المكررة.

**السيرفر وقاعدة البيانات**
- تتبع الاستعلامات البطيئة وحل الـ N+1.
- مراجعة الـ indexes على الجداول الكبيرة (attendance, payments, wa_messages_log).
- cache لأرقام الداشبورد (Redis موجود أصلاً).
- توليد الـ PDF بـ Puppeteer: إعادة استخدام نفس المتصفح بدل فتح واحد جديد كل مرة.

**الديسكتوب**
- سرعة فتح البرنامج، وإعدادات PostgreSQL المناسبة لأجهزة العملاء.
